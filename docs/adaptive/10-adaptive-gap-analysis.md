# 10 — Adaptive ERP Gap Analysis

Every row grounded in [`02-current-state-assessment.md`](02-current-state-assessment.md). Priority: **P0** = blocks the Configuration Engine from working at all; **P1** = blocks a specific, real Customer Profile answer from being honest; **P2** = real but deferrable without compromising the core Adaptive ERP claim.

| Capability | Current State | Target State | Gap | Risk | Recommended Approach | Priority |
|---|---|---|---|---|---|---|
| Per-company module visibility | `ENABLED_MODULES` is one global, code-level list (§2.4, §2.7) | Per-company `configuration_profile` determines visible modules | Full gap — no per-company mechanism exists at all | Building this wrong (e.g., hiding a module a company has real historical data in) risks data loss perception — must be additive/visibility-only, never destructive (§05 §5.4) | New `configuration_profile` + `configuration_catalog_item` tables (§06.3); nav-visibility layer over `NAV_CONFIG` (§02 §2.5) | **P0** |
| Customer Profile storage | Only `Company`'s narrow compliance fields (§2.2) | Full A–J profile (§03) | Full gap | Low if kept as a separate table (§06.3) — avoids risk to `Company`'s high-traffic shape | New `company_profile` table, 1:1 with `company.id` | **P0** |
| Sizing Engine | Does not exist | Deterministic, versioned, explainable scoring (§04) | Full gap | Medium — a wrongly-tuned threshold produces a bad recommendation, but is safe by design (never auto-applied, always reviewed) | New service, pure-function core, thresholds as data not code (§04 §4.3) | **P0** |
| ERP Blueprint | Does not exist | Versioned, approvable record (§05) | Full gap | Low — additive, immutable-once-approved by design | New `erp_blueprint` table + approval permission | **P0** |
| Configuration Engine (Blueprint → real rows) | Does not exist; manual Settings clicking is the only path today | Orchestrates existing application services (§06.1) | Full gap | Medium — must strictly reuse existing services, never a parallel write path (§06.1), or it silently diverges from real business rules over time | New orchestration layer only; zero new business logic | **P0** |
| Branch management | Schema + auth support real; **no update/delete API, zero frontend UI** (§2.3) | Full branch CRUD, reachable from Settings and from Blueprint provisioning | Partial — data model exists, management surface doesn't | Medium — any company whose Growth Blueprint calls for a second branch is currently unactionable without direct DB access | Add `PATCH`/`DELETE /companies/{id}/branches/{branch_id}`, build the missing Settings UI | **P0** (blocks the Growth Path worked example in §07 §7.3 from being real) |
| Cost Center management | Table + JE-line wiring exist; **no CRUD API/UI at all** (§2.3) | Full CRUD, so "cost center tracking" can be a real Blueprint feature flag | Partial — closest to "already built, just missing the last mile" of any gap on this list | Low — small, isolated, no schema change needed | Add `CostCenterService`/routes/UI following the existing `TaxRate` CRUD pattern almost exactly | **P1** |
| Approval workflow beyond PO | Only `Company.po_approval_threshold` gates Purchase Orders; nothing for vendor bills, sales orders, or journal entries (§2.4) | A generic, configurable approval-gate concept the Blueprint's "Approval Complexity" dimension (§03 §H) can actually turn on | Full gap for anything beyond PO | Medium — if the Customer Profile asks "how much approval rigor do you need" (§03 §H) and the honest answer is "only PO-level exists," the Sizing Engine must say so explicitly (FUTURE CAPABILITY), never imply broader support | Do not build a generic approval engine speculatively; wait for real customer demand signal via the Growth Review process (§09), then design narrowly | **P2** |
| Multi-currency | Schema placeholder only — `currency_code` field exists, no `exchange_rate`, not user-settable except on Payment (§2.4) | Either a real multi-currency feature, or an honest, permanent FUTURE CAPABILITY answer in the Customer Profile | The gap itself isn't the problem — the risk is a Blueprint ever implying this works when it doesn't | High reputational risk specifically if this is ever mis-stated to a customer, since it's Financial software | Customer Profile must never let "multi-currency: yes" silently pass into an approved Blueprint without a clear, visible caveat | **P1** (honesty gap, not a build gap) |
| Department entity | Does not exist at all (§2.3) | Either build a minimal `Department` table, or permanently scope Organization profiling to Branches/Cost Centers only | Full gap | Low — this is a genuinely optional feature; many SME customers won't need formal department hierarchy | Do not build speculatively (Principle: configuration > custom code, but *building* a Department module is a Core-capability decision, not a configuration one — see §06.5 tier "CUSTOM DEVELOPMENT") — revisit only against real demand | **P2** |
| Employee / HR data | `Partner.is_employee` + `job_title` only, no payroll, no department link (§2.3) | Documented FUTURE CAPABILITY in the Customer Profile (§03 §J); no build committed | N/A — correctly scoped already, not a gap to close, a boundary to hold | Low, as long as sales/onboarding never implies payroll support exists | No action — this is working as intended; the risk is entirely in how it's *sold*, not in the code | **P2** (governance, not engineering) |
| Edition/package concept | Does not exist anywhere (§2.4) | Editions as labels over Configuration state (§07 §7.1) | Full gap, but low-risk by design — it's presentation over data that already needs to exist for other reasons | Low | No separate build — falls out of `configuration_catalog_item` + `configuration_profile` (§06.3) once those exist; editions are a naming/UI exercise on top | **P1** |
| AI provider abstraction | No AI/LLM integration anywhere; one architectural precedent (`IZatcaGateway` Protocol) that isn't fully wired end-to-end even for its own original purpose (§2.8) | `AIProviderPort` Protocol + swappable adapters (§08 §8.3) | Full gap, but explicitly the *last* thing this roadmap builds (§11) | Low if built after the deterministic engine is proven (per governing principle: AI advisory only, Core works without it) | Follow the ZATCA Protocol shape; also worth actually finishing the ZATCA dynamic-switch wiring as a small, unrelated but instructive fix — noted here as a related opportunity, not committed | **P2** (by design — sequenced last, not because it's unimportant) |
| Rate limiting | None anywhere in the Core (confirmed) | At minimum, rate limiting on any future AI-calling endpoint | Full gap, currently latent (no cost-incurring endpoint exists yet to expose it) | Becomes real risk the moment Stage 7 (AI) ships without it — an unbounded loop against a paid AI API is a real cost/outage exposure | Must be a stated acceptance criterion for Stage 7, not deferred past it | **P1** (contingent — P0 *if and when* Stage 7 starts) |
| Backend localization beyond name/name_ar | Only field-pair pattern on 7 entities; no bilingual error messages, no backend-driven localization layer (§2.4) | Not required for Adaptive ERP specifically — Arabic-first is already a frontend-level property (836/836 key parity) | Not a blocking gap for this initiative | Low | No action needed for Stage 1–6; revisit only if Blueprint-generated content (e.g., AI-narrated recommendations, §08) needs bilingual output, which is a Stage 7 concern | **P2** |
| Wizard/multi-step UI pattern | Does not exist anywhere in the frontend (§2.5) | The Customer Profile / Blueprint review flow (§09) needs one | Full gap | Low-Medium — genuinely new frontend component category, real but bounded effort | Build using existing primitives (`FormView`, `<Can>`) plus the already-installed-but-unused `react-hook-form`+`zod` (§2.5) — this is the natural first real use of those dependencies | **P0** (blocks any UI for this entire initiative) |
| CI / regression safety net for this work | Now exists and green (Stage 0 Closure) | Same CI extended to cover new modules as they're built | No gap — already solved | N/A | Extend `ci.yml`'s existing test run as new test files are added; no new CI architecture needed | Resolved |
| Backup/restore/DR for the Golden Core | Now exists and proven (Stage 0) | Extend the same backup procedure to cover new Adaptive tables (automatic — `pg_dump` backs up the whole database, no per-table config needed) | No gap | N/A | No action needed — already correct by construction | Resolved |
