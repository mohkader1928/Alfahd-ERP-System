# 08 — AI Opportunities

Governing rule, restated because it's the whole point of this document: **AI must never be added because it's fashionable to have.** Every idea below is scored on whether it does something a deterministic, traditional ERP genuinely cannot do as well — not on whether AI *could* be involved. Several real, tempting ideas are marked LATER or FUTURE precisely because today's honest answer is "a deterministic feature would do this equally well, build that first." Confirmed starting point: **zero AI/LLM integration exists anywhere in the Core today** ([`02-current-state-assessment.md`](02-current-state-assessment.md)) — every idea here is genuinely new, not an extension of something existing.

## 8.1 Classification key

- **NOW** — could reasonably be built once the Configuration Engine (§06) is deterministic and proven; AI is advisory only, and a working non-AI path exists in parallel.
- **LATER** — real value, but depends on a Core capability that doesn't exist yet, or on enough operating history/data to be trustworthy.
- **FUTURE** — plausible eventually, not close to justified today; often because it needs a Core module that doesn't exist (payroll, manufacturing, CRM — see [`03-customer-profile-spec.md`](03-customer-profile-spec.md) §J).

## 8.2 The list

| Idea | Class | Business value | Technical complexity | Risk | Data requirements | Is AI actually necessary? |
|---|---|---|---|---|---|---|
| **Company setup assistant** — natural-language front end to the Customer Profile wizard ("tell us about your business" in free text → pre-filled profile fields) | NOW | Real: lowers the friction of a 10-section profile form, especially valuable in Arabic-first sales conversations | Moderate — a well-scoped extraction task against a fixed schema (§03), not open-ended | Low, if output always lands in the *same* reviewable profile form a human would fill manually — never silently submitted | None beyond the conversation transcript itself; no historical company data needed | No — a good form UX gets most of the value. AI adds convenience, not capability. Build the form first (it's needed regardless, per §06.2); layer this on top only once the form exists and is proven. |
| **Configuration recommendation** — AI proposes Sizing Engine inputs or explains its outputs in more natural prose | NOW | Real, directly serves the "explainable decisions" commercial requirement (§04 §4.4) | Low — it's a presentation/explanation layer over an already-deterministic engine, not a decision-maker | Low by construction: the deterministic Sizing Engine (§04) already produces the decision and the structured reason; AI only rephrases, never re-decides | The Sizing Engine's own rule set + the specific Customer Profile — no cross-customer data needed | Partially — the deterministic engine must exist regardless (it's the actual product); AI's contribution here is UX polish on an already-complete feature, genuinely valuable but not load-bearing |
| **Anomaly detection** (unusual transaction patterns, e.g. a journal entry far outside a company's historical norm) | LATER | Real, once a company has enough transaction history for "normal" to mean anything — a brand-new company has no baseline | High — needs real statistical/ML work, not a prompt; false positives erode trust fast in financial software | Medium — a wrong "anomaly" flag on a real transaction is a trust cost, not just an annoyance | Meaningful transaction history per company (months, not days) — doesn't exist for a newly-provisioned customer | Yes, this is a genuine ML/statistics problem, not a place a general-purpose LLM prompt does the job well |
| **Financial explanation** ("why did my cash balance drop this month?" in natural language, grounded in real GL data) | NOW (constrained) | Real — directly extends the existing fiscal-year-aware Dashboard (§02 §2.6), which already computes the numbers; explaining them is additive | Moderate — must be grounded strictly in real query results (the actual GL/dashboard data), never left to free-form generation, or it becomes a compliance risk in financial software | Medium if not grounded correctly; low if the AI only ever narrates numbers a deterministic query already computed and never asserts a number itself | Read access to the same data `DashboardService`/reporting already exposes — no new data pipeline | Yes for the *narration*, but the underlying numbers must always come from the existing deterministic reporting layer, never be computed by the AI itself |
| **Management insights** (proactive "here's what's worth your attention" summaries) | LATER | Real, but easy to make noisy/generic if built before Anomaly Detection has a real signal to summarize | Moderate-High — depends on Anomaly Detection and enough Dashboard history existing first | Medium — same trust-erosion risk as Anomaly Detection if wrong | Depends on Anomaly Detection existing | Partially — meaningfully better than a human eyeballing the dashboard only once there's a real detection layer underneath it |
| **Natural-language reporting** ("show me sales by customer for Q2, but only for the branch in Riyadh") | LATER | Real productivity value once a company has enough branches/segments (§03 §B) for ad hoc slicing to matter — for a 1-branch company this is over-engineering | High — needs a safe, bounded query-generation layer against the real schema, with strict guardrails against arbitrary SQL | Medium-High if not tightly bounded (a wrong query silently returning wrong numbers in financial software is a serious risk) — must only ever compose from a pre-approved set of report primitives, never generate raw SQL | The existing reporting layer's data, plus a well-defined "safe query vocabulary" that has to be built first | Yes, genuinely — this is a real natural-language-to-structured-query problem, but the guardrail work (§ risk column) is the harder and more important half of building it correctly |
| **Transaction assistance** (AI drafts a journal entry or invoice from a description) | FUTURE | Plausible value, but the Core's existing document-entry UX (quotation → order → invoice, already reasonably fast) is not an obviously broken workflow that needs AI to fix | High, and the risk profile is the worst on this list — a wrong AI-drafted financial document, even "just a draft," normalizes trusting AI output on money movement | High — this is exactly the kind of AI use the governing spec's non-negotiable rules exist to prevent: "AI must never bypass authorization, RLS, business validation, or audit controls" is trivially satisfied by *routing the draft through the normal document-creation service*, but the temptation to let AI shortcut validation is real and must be resisted explicitly | Requires broad read access across partners/products/pricing — a genuinely larger data-exposure surface than any NOW/LATER item | Not clearly — the existing forms are not the bottleneck for a typical SME's transaction volume; revisit only if real usage data says otherwise |
| **Onboarding** (guided, AI-assisted walkthrough after go-live) | LATER | Real, but depends on the wizard/Blueprint UI existing first (§06, §09) — there's nothing to guide a user through yet | Low once the underlying UI exists | Low | None beyond the Blueprint itself | No — a well-designed guided UI (checklists, tooltips) gets most of the value without AI; AI adds a conversational layer on top, once there's something to be conversational about |
| **Data quality** (flagging incomplete/inconsistent master data — e.g., products with no cost price, partners with no tax number) | NOW | Real and genuinely cheap to build — this is closer to rules-based validation than "AI" | Low | Low — these are deterministic completeness/consistency checks, not judgment calls | Existing master data only | **No — this should be a deterministic feature, not an AI feature.** Flagged here explicitly as the clearest example in this whole list of "don't reach for AI when a normal validation rule does the job." |
| **Forecasting** (sales/cash-flow projection) | LATER | Real value for growth planning (ties directly to §03 §G Growth) | High — legitimate time-series/statistical work, and needs meaningful transaction history (same constraint as Anomaly Detection) | Medium — a wrong forecast used for real business planning has real consequences; must always be presented as a projection with stated assumptions, never as a number to act on blindly | Meaningful historical transaction volume — absent for new customers | Yes, this is a real quantitative-methods problem worth doing properly rather than faking with a prompt |
| **Intelligent workflow recommendations** (e.g., "companies like yours typically also enable X") | FUTURE | Plausible, but requires a meaningful population of *other* Adaptive ERP customers with comparable profiles to learn from — doesn't exist yet, and raises cross-customer-data-use questions that need their own privacy/consent design before being touched | High, and gated on a data-governance question this document isn't the place to resolve | Medium-High — any cross-customer signal must be aggregate/anonymized only; a leak of "customer A's configuration influenced customer B's recommendation" in an identifiable way is a real trust and possibly contractual problem | Aggregate data across many customers — doesn't exist at Adaptive ERP's current (zero) customer count | Revisit once there's a real customer base; not answerable in the abstract today |

## 8.3 Provider independence — the architectural boundary (governing spec §7, §13)

Every NOW/LATER item above sits behind a single abstraction, matching the pattern already proven (if not yet fully wired end-to-end) by the ZATCA gateway (`IZatcaGateway` Protocol — [`02-current-state-assessment.md`](02-current-state-assessment.md) §2.8):

```
AIAdvisoryService (application layer, module company_profile or a new ai_advisory module)
        │  depends only on:
        ▼
AIProviderPort (Protocol — defined once, in backend/src/shared/ai/)
        │  concrete implementations:
        ├── ClaudeAdapter
        ├── OpenAIAdapter
        ├── LocalLLMAdapter
        └── NoneAdapter  (ai_provider = "none" — every AI-touching feature above
                           degrades to "not available," ERP Core keeps working 100%)
```

- **What the system sends to a provider**: only the specific structured input each feature needs (e.g., the Customer Profile fields for setup assistance, the Sizing Engine's own reasons for recommendation narration) — never a raw database dump, never secrets, never more than the feature's own documented data-minimization scope.
- **What it receives**: structured output only (never raw SQL, never a document ready to post without going through the same validation/authorization path a human-created one would).
- **Where validation happens**: always in the deterministic layer underneath (Sizing Engine, reporting layer, document-creation service) — never trusted from the AI response directly. This is the literal mechanism that makes "AI must never bypass authorization, RLS, business validation, or audit controls" true by construction rather than by policy.
- **Where authorization happens**: the AI call always executes inside the same request's `AuthContext` as the human who triggered it (§06.6) — it is never a privileged, cross-company, or unauthenticated code path.
- **Provider outage**: every feature above must degrade to "temporarily unavailable, here's the manual equivalent" — never to a system-wide failure. This is directly testable (`ai_provider = "none"` integration tests, per [`10-adaptive-gap-analysis.md`](10-adaptive-gap-analysis.md) and the testing plan this implies for whichever Stage actually builds Stage 7).

## 8.4 What this document explicitly refuses to recommend

Adding a general-purpose chat assistant "because ChatGPT exists" — the governing spec's own example of what not to do. Every item in §8.2 is scoped to a specific, bounded task with a specific data contract and a specific fallback. None of them is "let the user ask the AI anything about their ERP data" — that shape of feature is exactly where "AI must never bypass authorization, RLS, business validation" becomes hardest to guarantee, and it appears nowhere on this list for that reason.
