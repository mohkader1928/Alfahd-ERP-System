# 12 — Architectural Principles

These govern every future Adaptive ERP stage. Where a principle is already being honored by something real in the Golden Core, that's cited — these are not abstract ideals, they're continuations of how this codebase already works.

1. **Golden Core Preservation.** `phase-one-v1.0.0` (`6b6403c`) is never rewritten, amended, reset, rebased, or force-pushed over. Every Adaptive commit lands as a new commit on top of it. Already true of every commit in Stage 0 and this Stage 1 — verified before and after each one.
2. **Configuration First.** If a customer need can be met by data (a `configuration_profile` row, a Blueprint decision), it is never met by a code branch or a per-customer fork. See [`06-configuration-engine-architecture.md`](06-configuration-engine-architecture.md) §6.4–6.5 for the exact boundary between what's code and what's data.
3. **Multi-Tenant Safety.** Every new table added by this initiative uses the same `TenantScopedMixin` + RLS `company_isolation` policy pattern already proven by 42 dedicated tests. No new isolation mechanism is ever invented — the existing one is already correct and already tested.
4. **Versioned Configuration.** Customer Profile, Sizing rule sets, and ERP Blueprints are never edited in place — every change is a new version, and the currently-active version is always traceable. See [`05-erp-blueprint-spec.md`](05-erp-blueprint-spec.md) §5.3.
5. **Explainable Decisions.** Every Sizing Engine recommendation carries a plain-language reason, tied to a specific Customer Profile answer and rule version — never a bare score. See [`04-erp-sizing-engine-spec.md`](04-erp-sizing-engine-spec.md) §4.4.
6. **Provider Independence.** No AI feature is ever load-bearing for Core function. Every AI-touching feature has a `NoneAdapter` fallback and a manual equivalent. See [`08-ai-opportunities.md`](08-ai-opportunities.md) §8.3.
7. **Backward Compatibility.** Existing companies (everyone on v1.0.0 today) get no default `configuration_profile` — absence of Adaptive configuration means "behaves exactly as today," never a silently-computed new default. See [`06-configuration-engine-architecture.md`](06-configuration-engine-architecture.md) §6.7.
8. **Upgrade Safety.** Migrating an existing company onto Adaptive Configuration is always an explicit, reviewed, approved action generated from that company's real current settings — never automatic, never silent.
9. **Auditability.** Every Configuration Engine write reuses `AuditLogRepository` — the same manual-but-real audit mechanism already used in 5 modules. No new audit table, no new audit convention.
10. **Reproducibility.** The same Customer Profile plus the same Sizing rule version always produces the same Blueprint recommendation — a pure-function core with no hidden state, independent of whether AI narration is enabled.
11. **Customer Growth Support.** Growth is a Configuration and provisioning event (a new Blueprint version, applied to the same running instance), never a migration to a different product. See [`07-editions-and-growth-model.md`](07-editions-and-growth-model.md) §7.2–7.3.
12. **No Customer-Specific Forks.** Every customer, regardless of edition label, runs the identical source code and schema. Differences live entirely in `configuration_profile` data. This is the literal mechanism, not just the intent, behind Principle 2 and Principle 11 both — it's what makes "adapts to you" different from "was customized for you."
